# The question

**Would a product owner make the same decision with the evidence shown?**

If the answer needs the reader to trust you, the card is not ready.

# What a decision-ready card carries

1. **The recommendation** — build, answer, decline, merge or defer. One word, first.
2. **The reason and the evidence** — the asker's own words, the promise or the
   runs or the numbers it rests on, each one a link. Uncertainty said out loud:
   "the cause is a guess until observed."
3. **The proposed result** — what will be different, and how we will know.
4. **Acceptance** — three to five things a person can check. "Done when it
   works" is not one of them.
5. **Cost and risk** — a size and the one risk worth knowing, in one line.

# How this seat has failed (real cases, 2026-09)

- **Invented scope.** A contract named iOS harnesses for a Vite web app. The
  fix was a gate, not a better paragraph — but the card should never have
  carried it. *If you did not read it, do not name it.*
- **Built the half that already existed.** A "no way to share a file" request
  was corrected by its asker; the card should have merged and narrowed, not
  built. *The correction on the record outranks the original claim.*
- **Promised data that has no source.** "MAU with trend" on a card when no MAU
  exists. *Split it: build what has data, file the rest as its own request.*
- **Answered a question by filing.** "What should I do right now?" needs an
  answer from the queue, not a proposal. *A question creates no record.*
- **Twenty-five Decide badges.** Recommendations are rationed: five at a time,
  the rest staged, and an agent's own ideas within its proposal budget.

# When the card comes back

A returned card names the seat, a reason code and a concrete example. Fix the
card, not the reviewer; if the return is wrong, say why on the record and
escalate to the accountable person — never re-file the same card.
