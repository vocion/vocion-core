# v0.6.0 — off Temporal: the cutover

**BREAKING.** v0.6.0 removes Temporal. Every flow, schedule and background job
runs on DBOS inside the app process, in schema `durable` of the app's own
Postgres. There is no workflow server, no worker container and no second
database to run, back up or upgrade.

## What moved where

| Was (Temporal) | Is (DBOS) |
|---|---|
| `scripts/temporal-worker.ts`, its container | The app process, when `VOCION_SCHEDULE_OWNER=1` (`libs/durable/executor.ts`) |
| A Temporal Schedule per automation, workflow trigger, mission, source | A row in `durable.workflow_schedules` firing `vocion.job.tick` with the job named in its context (`libs/durable/jobs.ts`) |
| `automationFire`, `sourceSyncWorkflow`, `missionScheduledCheck`, `scheduledWorkflowTrigger`, `evalRefreshWorkflow`, `bulkBriefRegenerate`, the reapers, retention, image sweep | Named jobs in `services/background/catalog.ts`, each with the retry its activity had |
| Langfuse retention, worker-run reaper, mission-run reaper, artifact image sweep (applied by the worker on boot) | `services/background/deploymentSchedules.ts`, applied when the executor starts, plus `durable-prune` (finished job runs older than a week) |
| The worker's 15-minute abandoned-fire sweep and 15-second notification drain | In-process timers on the executor (`services/background/housekeeping.ts`) |
| `startDelay` on the coalesced fire | `afterMs` on the job: a durable sleep that survives a deploy |
| Temporal's `overlap: SKIP` on automation schedules | A tick that finds the automation's last fire still running is skipped (`scheduleFireInFlight`) |
| `catchupWindow: 1 hour` | No backfill: a missed tick is not replayed; the next tick fires |

## Exactly one executor, and no double fires

- **One process runs runs and fires schedules**: the app with
  `VOCION_SCHEDULE_OWNER=1`. Any other process — a dev server pointed at a
  tunnelled production database, the tooling container that applies a
  workspace — is a client only. A production app without the flag says so in
  its log at error level.
- **Each tick runs once.** A tick's run id is
  `sched-<schedule>-<tick time>`, so a restart, a deploy or a second poll of
  the same tick finds the run already there.
- **Nothing to double up during the cutover**: Temporal is removed in the same
  deploy that creates the DBOS schedules, so there is never a moment with two
  schedulers. The Temporal schedules die with the Temporal containers.

## The cutover, in order

1. **Deploy v0.6.0.** The bootstrap's `pg_dump` runs first, as always, and
   covers schema `durable`. Migrations run. The app starts and, with
   `VOCION_SCHEDULE_OWNER=1`, launches the executor, which applies the
   deployment schedules (`[durable] deployment schedules {applied: [...]}`).
2. **The workspace apply** (`VOCION_SCHEDULE_OWNER=1` on the apply container)
   writes every automation, workflow, mission and source schedule into
   `durable.workflow_schedules`. A schedule that cannot be written is an error
   on the apply result by name; the rest of the apply still lands. A paused
   automation's schedule is re-asserted paused.
3. **Remove the Temporal services** from the instance compose
   (`temporal`, `temporal-ui`, `temporal-postgres`, `temporal-worker`) and
   `docker compose up -d --remove-orphans`. Keep the `temporal_pg_data`
   volume until the first verified week, then `docker volume rm` it.
4. **Unset** `ENABLE_TEMPORAL_WORKER`, `VOCION_TEMPORAL_ADDRESS`,
   `VOCION_TEMPORAL_NAMESPACE`, `VOCION_TEMPORAL_CONNECT_TIMEOUT_MS`. They are
   read by nothing.

Forward only: there is no path back to Temporal in v0.6.x. A run in flight on
Temporal at the moment of the deploy is lost with it; the abandoned-fire sweep
closes its `automation_run` row on the executor's first pass, and the next tick
fires as usual.

## Verify on the box

```bash
curl -s https://<host>/version.txt                       # the new sha
docker ps --format '{{.Names}}' | grep -i temporal        # nothing
docker logs vocion-app 2>&1 | grep -E '\[durable\] (executor up|deployment schedules)'
# every schedule, and when it last fired
docker exec vocion-postgres psql -U postgres -d vocion -c \
  "select schedule_name, schedule, status, last_fired_at from durable.workflow_schedules order by 1"
# each tick once: no schedule has two runs for one tick time
docker exec vocion-postgres psql -U postgres -d vocion -c \
  "select workflow_uuid, count(*) from durable.workflow_status where name = 'vocion.job.tick' group by 1 having count(*) > 1"
```

## Dev

Set `VOCION_SCHEDULE_OWNER=1` in `.env.local` only when the database is your
own. `DURABLE_MODE=memory` runs everything in-process with no Postgres
schema at all. `DURABLE_PG_URL=postgres://… npx vitest run src/libs/durable`
proves the engine against a throwaway Postgres (never the production tunnel).
