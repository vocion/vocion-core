# v8.0.0 — when lives in automations: the upgrade

**BREAKING.** 8.0 has one place for *when* (automations, on a named clock)
and one for *why and where the result goes* (missions, with `deliver:`). The
decision and the red team behind it are in
[ADR 0008](../adr/0008-when-lives-in-automations.md).

## Release notes

- **Schedules read on a named clock.** `when.timezone` takes an IANA zone, or
  `workspace` for `defaults.timezone`; with neither, a version-2 workspace's
  schedule is read in its own zone. "6:30am" stays 6:30am through daylight
  saving.
- **Results go out when a check finishes.** A mission's `deliver: {email}`
  mails the briefing a check published. A check that published nothing sends
  nothing, and a failed check sends a short note instead of an older
  briefing.
- **No more double fires.** A mission's own `schedule:` is gone. It fired the
  same check a second time, with none of an automation's guards, wherever an
  automation also checked it: 17 places in core's own plugins and templates.
- **Marketing.** The Marketing app runs on the workspace's clock, sends a
  Saturday summary, and between mornings raises alerts (ad limited, spend off
  budget, first conversion) from a four-hourly guard that uses no model.
- **The daily report** says when the briefing it carries is not new.
- **The automation page** shows the next run.

## What breaks

| Was | Is | If you do nothing |
|---|---|---|
| `workspace.yaml` `version: 1` | `version: 2` | Version 1 loads through 8.x with warnings; removed in 9.0. |
| A mission's `schedule:` | An automation: `when: {schedule, timezone}`, `do: {checkMission}` | In a version-1 workspace it runs as `<mission>-check` (UTC), or is dropped when an automation already keeps the mission; in version 2 it is an error. |
| Every cron read in UTC | Read in `when.timezone`, else the workspace zone (version 2, and plugins) | Version-1 workspaces keep UTC. Migration 0220 pins existing rows to UTC. |
| A `daily-team-report` mail timed after a check | The mission's `deliver:` | The timed mail still sends, and says when its briefing is old. |
| Plugin missions with `schedule:` (wiki, data rooms, finance, growth loop, software factory, company templates) | Their cadence is an automation file in the plugin, pinned to UTC | Nothing: same time, one fire instead of two where there were two. |

## The two migrations

### The database: migration 0220 (runs with every deploy)

1. Adds `mission.deliver jsonb`.
2. Copies every unzoned schedule (`automation.when_config`) and every mission
   cron to `migration_0220_backup`.
3. Sets `timezone: UTC` on every schedule that named none. That is what they
   meant, so nothing moves.
4. Inserts `<mission>-check` for each mission cron that no active automation
   keeps (`timezone: UTC`, described "Moved from the mission's schedule: in
   8.0.0").

It is safe to replay, which `migrate.sh` does on every deploy. The old
`mission-schedule-…` durable schedules keep firing until the next
`workspace:apply`, which removes them and schedules the automations on their
clocks. So apply right after the deploy.

### The manifests: the codemod

```bash
# What it would change (a diff), then apply it:
npm run migrate:automations -w @vocion/core -- path/to/workspace
npm run migrate:automations -w @vocion/core -- path/to/workspace --write
# Or move simple crons onto the workspace's own clock instead of pinning UTC:
npm run migrate:automations -w @vocion/core -- path/to/workspace --write --localize
```

It is idempotent (a second run changes nothing) and edits line by line, so a
file changes only where it must. Each change prints a note.

- **`version: 1` → `2`.**
- **Unzoned schedules** get `timezone: UTC`. With `--localize`, a cron with one
  minute and same-day hours is rewritten onto `defaults.timezone` at today's
  offset instead.
- **A mission's `schedule:`** becomes `automations/<slug>-check.yaml`.
  - It is removed instead when an automation already keeps it.
  - A workspace's changed cadence on a plugin mission becomes its own copy of
    the plugin's automation.
- **A timed `daily-team-report` mail** becomes the mission's
  `deliver:`. Only when exactly one check runs in the hour before it; the
  rest are named in the notes, to move by hand.

Then run `npm run workspace:check -w @vocion/core -- path/to/workspace`.

## Rolling out

The coordinator owns pins and deploys. The order:

1. **Core.** Merge to main; semantic-release cuts **v8.0.0**.
2. **Each environment** (dev.app.vocion.ai, app.vocion.ai, agents.metacto.com):
   pin v8.0.0 → deploy. Migration 0220 runs before the swap. Then run
   `workspace:apply` for every workspace. Version-1 manifests apply with
   warnings and fire exactly as before.
3. **Workspaces.** Run the codemod on each workspace repo in its own PR, and
   merge it only once that environment serves 8.0.0:
   - Meta-CTO/metacto-vocion-agents for agents.metacto.com;
   - the vocion-cloud workspaces for dev and prod.

   Check each with `workspace:check`, then apply.
4. **Watch.**
   - The automation pages show the next run on the right clock.
   - Every former mission cron shows as `<mission>-check`, with a run log.
   - No check fires twice per tick.

## Rolling back

Deploy the previous 7.x pin, then run `workspace:apply`. 7.x reads every cron
in UTC and ignores `timezone` and `deliver`. To undo the data as well:

```sql
DELETE FROM automation WHERE description = 'Moved from the mission''s schedule: in 8.0.0 (migration 0220).';
UPDATE automation a SET when_config = b.data
FROM migration_0220_backup b
WHERE b.kind = 'automation.when' AND a.org_id = b.org_id AND a.slug = b.slug;
UPDATE mission m SET schedule = b.data ->> 'schedule'
FROM migration_0220_backup b
WHERE b.kind = 'mission.schedule' AND m.org_id = b.org_id AND m.slug = b.slug;
```

`mission.deliver` can stay: 7.x does not read it. A workspace repo that was
already moved to version 2 must be reverted to its pre-codemod commit before
a 7.x apply, because 7.x refuses `version: 2`.
